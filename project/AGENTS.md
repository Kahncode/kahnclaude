## Critical Rules

### 0. Never Publish Sensitive Data

<!-- GUIDE: Non-negotiable security rule
Format: Bullet list of absolute prohibitions
Always include: passwords, API keys, tokens, .env files, credentials -->

- NEVER commit passwords, API keys, tokens, or secrets
- NEVER commit `.env` files — always verify `.env` is in `.gitignore`
- Before ANY commit: verify no secrets are staged
- Use `security-check` agent to scan for exposed secrets

### 1. Ask Before Deploying

<!-- GUIDE: Operational safety rule
Format: Explicit requirement to wait for user confirmation
Always include this unless the project uses automated deployment with explicit guardrails -->

- NEVER auto-deploy, even if the fix seems simple
- Always wait for explicit confirmation: "yes, deploy this"

### 2. Quality Gates

<!-- GUIDE: Code quality thresholds
Format: Limits on code size, test coverage, or other metrics
Examples: file/function size limits, test pass requirements, linter rules -->

- No file > 300 lines (split if larger)
- No function > 50 lines (extract helpers)
- All tests must pass before committing

### 3. Git Workflow

<!-- GUIDE: Branching and commit strategy
Format: Show the expected git workflow (branch creation, naming conventions) and the commit message convention
Always include: feat/, fix/, docs/, refactor/ branches and Conventional Commits unless the project uses another convention (the commit, pr and issue skills follow what is written here) -->

```bash
# Always branch first — before editing any files
git checkout -b feat/<task-name>
```

- `feat/<name>` — new features
- `fix/<name>` — bug fixes
- `docs/<name>` — documentation
- `refactor/<name>` — refactors

Commit messages and PR titles follow [Conventional Commits](https://www.conventionalcommits.org): `type(scope): subject` (`feat`, `fix`, `docs`, `refactor`, `test`, `chore`). Keep commits focused: one logical change each.

- Use the documenter agent to keep `docs/ARCHITECTURE.md` in sync with significant changes

Format: Symptom → Check → Action
